# Use loadout with Codex

Most of loadout works the same in both agents: the kit, your personal layer, the daily sync and the commands do not depend on which agent you use. This page holds what only applies to Codex: how to switch it on, the version it needs, its hook approval and the places where it stays different. What Codex receives is listed per file in the [personal layer](../reference/personal-layer.md), per setting in the [hooks](../reference/hooks.md) and [profile](../reference/profile-format.md#in-codex) references.

## Switch it on

On a new machine, bootstrap asks which coding agents to set up, Claude Code, Codex or both, right after the personal layer question. With Codex and `--install`, it installs Codex too (through mise); without `--install` it reports Codex as missing. Scripts can pass the choice: `bootstrap.sh --install --agents codex` (or `claude`, or `claude,codex`). On a machine set up before this choice existed (an existing personal layer), bootstrap asks only when `codex` is on your PATH (in WSL, also a Windows `codex.exe`); with no Codex seen it asks nothing and sets up Claude Code. A personal layer you clone that already holds a choice (`targets.json`) decides without the question, and bootstrap says so; `--agents` wins over it ([bootstrap flags](../reference/cli.md#loadout-bootstrap)).

With VS Code's Codex extension and no Codex CLI, loadout sets Codex up for the extension. That is a full setup, plugins and hooks included: the Codex CLI next to it is optional, and with `--install` in a terminal bootstrap asks (default No) ([Codex in VS Code without the CLI](vscode.md#codex-in-vs-code-without-the-cli), [ADR 0033](../adr/0033-codex-for-the-vscode-extension-without-its-cli.md), [ADR 0038](../adr/0038-codex-extension-loads-plugins-and-reviews-hooks.md)).

To switch an agent on or off later:

```bash
loadout configure set target codex on
loadout configure set target claude off
```

One agent must stay on. Switching an agent off uninstalls nothing; loadout just stops setting it up. The choice is stored in your personal layer (`targets.json`), so it follows you to every machine. loadout needs codex 0.161 or newer.

**Codex only.** Without Claude Code, bootstrap does not install Claude Code and skips everything that belongs to it: the links under `~/.claude`, the Claude settings, its plugins and `adopt`. In a repo that has no `.loadout.json`, `loadout init` and `loadout profile` write no Claude Code files either, and repo skills go into `.agents/skills`; a repo that names Claude Code in its `.loadout.json` gets those files even from you ([ADR 0030](../adr/0030-repo-files-follow-the-repos-agents.md)). `loadout check` and the daily sync then look at Codex only. Codex still gets the plugins the kit enables, the rules, your personal layer and the tools. Add Claude Code later with `loadout configure set target claude on`; if Claude Code is not installed yet, it tells you to run `loadout bootstrap --install`, which installs and sets it up (VS Code's Claude Code extension counts: loadout then sets Claude Code up with the extension's binary).

The first run clones each plugin marketplace into Codex, which can take a few minutes on a slow connection; a progress line names each step (with `--verbose`, or without a terminal, one line each). Ctrl+C is safe: run the command again and it continues where it stopped. Only one loadout run sets up Codex at a time.

Then approve loadout's hooks once in the Codex CLI: start `codex` and trust them when it asks about new or changed hooks, or review them first in `/hooks` (in VS Code's Codex extension, approve them there; see [Codex in VS Code without the CLI](vscode.md#codex-in-vs-code-without-the-cli)). Codex runs plugin hooks, and the Serena hooks loadout puts into `~/.codex/hooks.json`, only after you approve them, and again after they change ([which hooks](../reference/hooks.md), [Serena's hooks in Codex](../reference/hooks.md#serenas-hooks-in-codex)).

## What Codex gets

The same kit and personal layer reach Codex. Where each part goes (the instruction block in `~/.codex/AGENTS.md`, `config.toml`, `~/.agents/skills`) is in [Personal layer](../reference/personal-layer.md#files); the plugins it installs are in [Included tools](../reference/included-tools.md); the type-check hook that stands in for Claude Code's LSP plugins is in [Hooks](../reference/hooks.md). Claude Code settings without a Codex equivalent (thinking mode, auto mode, the permission list) have no effect on Codex.

## What stays different

- **Hooks need your approval once**, when Codex asks at start or in `/hooks` (see above).
- **Commit attribution.** Codex adds `Co-authored-by: Codex` to commits when your ChatGPT account has commit attribution turned on. That is an account setting, not a config key: turn it off in your ChatGPT account settings. loadout's rule against AI attribution reaches Codex through the instruction block, but cannot remove the trailer.
- **Context7 without a login.** The plugin's Context7 address asks Codex for an OAuth login; loadout sets the plain address for Codex instead, which works without one. Anonymous use has Context7's lower rate limit, so loadout lists an optional `codex mcp login context7` until you log in.
- **Logins and approvals are named where you work.** Bootstrap's "Still to do", `loadout configure set target codex on` and `loadout check` list what is still open in Codex: the hook approval in `/hooks` or, in the extension, the hooks icon and Allow all (until you approved them, and again after loadout's hooks change) any MCP server that waits for a login (`codex mcp login NAME`), and any marketplace or plugin Codex still lacks, for example after a large clone timed out (`loadout update` retries them). With only VS Code's Codex extension, the login is in the extension (gear, MCP servers, Authenticate), and the hooks are approved there too ([Codex in VS Code without the CLI](vscode.md#codex-in-vs-code-without-the-cli)). loadout does not approve hooks for you: that approval is Codex's safety gate.
- **Serena already set up?** If you followed Serena's docs (`serena setup codex`), loadout uses your Serena server whatever its name and adds no second one, and it adds only the Serena hooks your `~/.codex/hooks.json` lacks ([Serena's hooks in Codex](../reference/hooks.md#serenas-hooks-in-codex)).
- **codebase-memory already set up?** The loadout plugin provides codebase-memory-mcp in both agents, so a server of yours is a second one. loadout recognises yours by its command, whatever its name:
  - `loadout check` names a Codex table (`Codex MCP NAME: runs codebase-memory-mcp next to the loadout plugin's`) or a Claude Code server (`codebase-memory servers: …`);
  - `loadout adopt` offers to remove it with a backup, but only while the plugin serves codebase-memory in Codex: installed and not switched off. Otherwise your table is the only codebase-memory server there and stays. A Codex table with settings of its own (`env`, extra `args`, timeouts, a fixed path) is only named, so you decide what to keep.

  What `codebase-memory-mcp install` wrote itself (its block in `~/.codex/AGENTS.md`, its Codex hooks, its hook scripts and agent file under `~/.claude`) is named as `codebase-memory installer: …` and offered for removal the same way, while loadout's plugin is installed (the agent file, known only by its name, is named and never offered): never without your yes, and `loadout restore` puts it back. Your own codebase-memory session or subagent hooks keep loadout's project pointer quiet, so it is not said twice ([ADR 0041](../adr/0041-own-codebase-memory-by-command.md)).
- **Serena's tools ask for approval.** Claude Code approves Serena's tools through loadout's hook; Codex asks before every `serena_repl` call. loadout asks you once whether Codex should approve them automatically (`codex_serena_approval`, default: ask each time); change it with `loadout configure prefs` ([Serena's approvals in Codex](../reference/preferences-format.md#serenas-approvals-in-codex)). Approvals you give yourself with "Always allow" stay yours: loadout keeps managing the server's table and leaves your `[mcp_servers.NAME.tools.*]` sections as they are ([ADR 0036](../adr/0036-codex-tool-approvals-and-serena-approval.md)).
- **MCP tools load on demand in Codex.** Unlike Claude Code, where loadout's plugin loads Serena's and codebase-memory's tools upfront (`alwaysLoad`), Codex has no per-server switch: whether it loads tools upfront depends on the model's tool-search support. So a session can claim "Serena is not available" without looking. loadout's instruction block tells Codex to search first; if it still does not use them, ask for them by name ("use Serena's find_symbol") ([ADR 0039](../adr/0039-serena-remind-tools-load-upfront-cbm-refresh.md)).
- **Serena's reminder covers shell searches.** Serena's own `remind` hook (on `Bash`) denies the 3rd grep without a Serena tool in between; the next call goes through. It runs from loadout's plugin behind the guard, which lets searches in config, docs, piped output and files outside the project through; until the installed plugin copy carries it, it runs from `~/.codex/hooks.json` ([Serena's hooks in Codex](../reference/hooks.md#serenas-hooks-in-codex), [ADR 0040](../adr/0040-serena-remind-skips-harmless.md)). loadout adds no hint of its own in Codex: Codex gives hooks no Grep, Glob or web tools, so there is no docs hint either ([Hooks](../reference/hooks.md#serenas-reminder), [ADR 0039](../adr/0039-serena-remind-tools-load-upfront-cbm-refresh.md)). Whether the hooks run in Codex subagents is not known yet.
- **Type checks run per edit** instead of a language server that keeps running. Large TypeScript projects can take a few seconds; after 20 seconds the check reports itself as skipped.

## Project trust

When the repo is for Codex (its `.loadout.json`, or your agents without one), `loadout init` and `loadout profile NAME` also set up Codex in the repo ([what each profile field becomes](../reference/profile-format.md#in-codex)). Codex reads a repo's `.codex/config.toml` only in a trusted project. Until you trust it, loadout prints the step: start `codex` in the repo once and accept the trust question. loadout prints the same step with only VS Code's Codex extension; this is Codex's project trust, not VS Code's workspace trust (Trust Folder & Continue). Whether the extension asks the project trust question itself is not confirmed yet, and the Codex CLI in VS Code's terminal does ask it. loadout never trusts a project for you. Like every repo write, these show a plan and ask first, and `loadout restore` undoes them ([Repo writes](../reference/cli.md#repo-writes)).
